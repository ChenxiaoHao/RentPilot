# RentPilot 参赛版范围和验收标准

版本：Day 1 v0.1，2026-10-27。依据用户确认的赛题 1、初赛表和 12–15 天安排形成。此文确定后续实现范围，今日不实现后端或修改前端；赛题账号内规则和资源仍有待核验项。

## 目标与定位

面向上海租住场景，用户用自然语言描述预算、工作地点、户型和通勤要求，系统把要求整理为可确认的条件，从有来源的数据中寻找方案；发生冲突时，解释调整一项条件的代价。用户比较方案、调整偏好并保存版本。

候选作品描述：RentPilot 可解释租住决策助手。主要验证点是需求约束、冲突识别和方案取舍，不宣称首创、真实房源供给或已经提升决策效率。

## 产品和技术边界

- 保留 Vue 3、TypeScript、Vite、Router、Pinia、Capacitor Android、既有页面与 Stitch 黑白灰、胶囊导航方向；第 2–3 天重点优化聊天、方案、对比及手机适配，不另建管理后台。
- 按原计划建立单体 Spring Boot + Spring AI 后端，使用一个找房助手和受控工具。暂不引入微服务、多 Agent 集群、向量数据库、搜索集群或自训模型。
- 房源是结构化数据，先用数据库查询和明确计算；图片理解、真实预约、支付、短信注册、真实推送不纳入本轮实现，原页面入口保留诚实说明。
- Android 用户端保留；建议复用同一 Vue 用户端提供受控云端 Demo，不另开发一套 Web 管理端。模型和后端 Web 服务密钥保留在服务端。
- 数据库首选与团队获批资源匹配的关系型数据库；PostgreSQL 是候选方案，具体产品和兼容版本在第 4 天初始化前核对，不在本日安装依赖或锁死云产品。
- 新增外部资源与带费用调用需要明确授权和预算；今日只记录准备情况。

## 三个核心模块

### 需求理解和冲突检测

识别月租预算、工作地、通勤上限、出行方式、出租方式、卧室数和生活偏好。保留每个条件的用户原文、提取结果及用户确认状态。硬条件和偏好分开：用户明确表示不能超出的预算不能被权重滑块或模型解释覆盖。

工作地点有歧义时先展示候选或追问；预算、通勤等关键字段缺失时不静默套用张江、5000 元或 30 分钟。多轮补充只更新本轮涉及的条件。用最新已确认条件发起规划，修改条件后旧结果标记为先前版本。

### 房源检索和方案权衡

工具检索数据库中的模拟房源，后端校验并计算。先筛选硬条件，再比较成本、通勤与可验证的生活偏好；可以返回 0、1、2 或最多 3 套有差异的方案，不为凑数造房源。

无解时基于实际查询结果提出只改变一项条件的建议，并展示改变的字段和前后值。用户确认前原条件不变。若路线或关键数据不可用，应返回“条件暂无法验证”，与“已验证无结果”分开。

费用按月租、已知物业费、交通估算和用户提供的生活预算分项展示；押金和预付租金作为入住资金单列，不全部混入每月生活成本。所有未知项和估算假设保留。

方案评分只能是有说明的规则结果，不声称客观居住质量或现实满意度。权重归一化和缺失项处理在实现前写清公式。条件相同的确定性计算应一致，模型负责说明而非编造数值。

### 可解释推荐和生活模拟

每个推荐链接到真实存在于当前数据库的 listingId，附匹配依据、未满足或未知条件、费用来源及路线来源和时间。模型输出经过结构和 ID 校验后才用于页面。

LifeSim 依据用户作息假设与可用路线展示场景。月通勤时间由单程时长、每日次数、工作日数计算，单位明确；节省时间必须有明确比较方案和相同假设。没有路线或作息数据时不填入虚构分钟、自由时间或满意度。

保存需求、权重、结果和数据来源的版本快照；查看旧版不改变当前方案，恢复旧版需要确认并保留历史。

## 核心流程

1. 用户输入找房需求，收到真实模型响应和结构化需求摘要。
2. 追问缺失或歧义信息，用户确认硬条件与偏好。
3. 发起规划任务，前端显示后端真实阶段或等待状态。
4. 查询房源与路线，计算费用和可选方案；允许无结果、部分数据或失败。
5. 用户查看依据和对比；有冲突时选择是否调整一项条件。
6. 重新计算并创建版本；LifeSim 复用同一方案数据与显式假设。
7. 保存版本，重启后仍可查看与比较，Android 与云端 Demo 使用同一后端规则。

## 初步数据和接口约定

这是第 4 天实现前的契约草案，当前项目没有这些接口。

| 对象或接口 | 关键约定 |
| --- | --- |
| RequirementSnapshot | 独立 ID、版本、硬条件、偏好、缺失字段、确认状态；月租单位 CNY/月，通勤单位分钟/单程 |
| Listing | 保留原编号、数据性质、位置验证状态、可空 GCJ-02 坐标、设施三态和导入批次；原始 CSV 不改 |
| RouteEstimate | 起终点、坐标系、方式、时长、距离、来源、时间、成功/不可用状态；以小区坐标推算时标明参考范围 |
| PlanSnapshot | 引用需求版本和房源 ID，保存费用、路线、假设、规则版本与原因；不只有一段聊天文字 |
| POST /api/conversations | 创建隔离会话，返回后端会话标识 |
| POST /api/conversations/{id}/messages | 返回回答、需求更新、缺失/待确认字段；模型异常有可识别错误 |
| GET /api/listings 与 GET /api/listings/{id} | 明确分页、排序和筛选；不把未设置条件变成默认限制 |
| POST /api/planning-tasks 与 GET /api/planning-tasks/{id} | 引用已确认需求版本、幂等键；返回任务状态和结果/错误 |
| GET /api/plans/{id} | 返回方案数据、来源与假设 |
| 版本、比较、偏好和收藏接口 | 第 9 天前补齐一致的资源标识与权限；前端通过统一数据服务访问，不再到处直接 import mock |

任务状态至少区分 QUEUED、RUNNING、NEEDS_INPUT、SUCCEEDED、NO_MATCH、FAILED；重试不应重复保存版本。可以先用轮询，SSE 仅在有明确体验收益时加入。进度不再按固定 2.75 秒假装完成。

## 数据要求

- 当前 CSV 实测 1500 条、38 列，编号唯一；14 条缺经纬度、423 条缺地铁步行距离。设施“是/否/未知”保持三态，空距离不能填 0。
- 位置参考真实小区不代表存在真实在租房屋；1486 条的来源声明不能替代逐条位置精度核验。地图与路线起点范围如实注明。
- 数据导入按来源和原房源编号幂等，保留映射、错误报告和校验；不手改 CSV 来凑演示结果。
- 不将小区到最近地铁站的步行时间当作到工作地点的通勤时间。
- 原数据限定演示使用。云端采用受控比赛 Demo，不作为真实租房平台运营；源码开源与数据/素材开放分别检查授权。

## 必须通过的验收

| ID | 检查 | 通过标准 |
| --- | --- | --- |
| A01 | 需求变化 | 不同预算、户型、工作地和多轮补充进入真实数据流，不再按消息条数返回固定推荐 |
| A02 | 硬条件 | 已确认硬条件不被悄悄修改；返回候选不得违反已验证硬条件；未知项单独列出 |
| A03 | 冲突 | 无结果与不可验证分开；修改建议展示前后值并等用户确认，其他条件不变 |
| A04 | 房源与数值 | 无不存在的房源 ID；费用/路线均有来源或明确假设，计算结果可复算 |
| A05 | 数据导入 | 1500 条导入并可查询，重复导入不重复；14 条空位置不出假点位；原文件哈希不变 |
| A06 | 版本 | 保存、比较和确认恢复可用，查看快照不恢复；输入变化不会把旧方案伪装为新结果 |
| A07 | 失败和并发 | 模型、路线超时可重试；旧请求不覆盖新条件；重复提交不生成重复版本；会话之间不能读取对方数据 |
| A08 | 手机体验 | 320/360/402/480 宽度无页面横向溢出；主要触控目标至少44px；Pixel 模拟器键盘和系统手势区域可操作 |
| A09 | 云端交付 | 通过华为云部署的受控 Demo 可访问；Android 使用同一规则；断网/缓存状态诚实提示 |
| A10 | CodeArts | 至少有真实、完整的任务记录，能连接需求、操作、变更、验证和部署结果；不伪造历史 |
| A11 | 参赛材料 | 初赛表每个已完成能力有对应证据；目标与实测区分；演示与代码一致 |

## 测试与证据设计

建立 30 个可复现案例：10 个单轮完整需求、10 个多轮补充、5 个条件冲突、5 个缺失/歧义/异常。保留人工标注的预期字段和判断依据，其中 20 个用于调试、10 个用于最终留出检查；此数量是工作计划，不是已测试成果。

记录字段提取准确情况、已验证硬条件满足情况、冲突检出和误报、错误房源引用、路线/费用计算误差、响应时间、失败率及调用量。模型、提示词、规则和数据版本一起记录。与同一案例上的普通筛选或无工具回答对照，避免用不同任务制造提升。

今日不填写任何准确率、节约时间或成本降低的实测数字。测试不能完全用模型自评替代人工答案。
